# Agent-Pay V1 Final Release — 2026-09

## Release status

**V1 FINAL — protocol + conformance + reference implementation**

Agent-Pay V1 is the financial control and payment-execution layer for the agentic internet. The V1 boundary with Agentic Trust Foundation is frozen.

**Project memory and forward roadmap:** `docs/roadmap/v1-complete-and-v2-roadmap-2026-09.md`

## V1 ownership boundary

ATF owns:

- identity;
- delegation;
- general authorization;
- capabilities;
- trust;
- consent;
- provenance;
- revocation.

Agent-Pay owns:

- financial spending policy;
- policy versions and decision evidence;
- budgets and reservations;
- human approval workflow;
- payment authentication boundary;
- payment instruments and routing;
- provider operations and idempotency;
- transaction lifecycle;
- double-entry-ready ledger;
- provider events/webhooks;
- settlement and reconciliation;
- financial audit and outbox notifications.

Agent-Pay never expands upstream authority. Approval cannot repair invalid authority or increase an upstream amount/scope bound.

## V1 security boundary

A payment requires:

1. authenticated Agent-Pay principal;
2. agent/account binding;
3. cryptographically verified ATF authorization evidence;
4. explicit payment scope;
5. positive maximum amount and matching currency;
6. validity/expiry;
7. valid revocation status;
8. Agent-Pay policy decision;
9. budget reservation;
10. required human approval;
11. provider idempotency and explicit ambiguous-outcome handling.

The reference implementation uses JWT/JWKS as an adapter profile. This does not freeze a universal ATF credential format.

## Non-goals of the V1 release

V1 does not claim:

- live PSP/bank/card-issuer interoperability;
- production card issuance;
- universal ATF token/signature wire format;
- jurisdiction-specific regulatory certification;
- production HSM/vault deployment;
- full dispute/chargeback operations;
- mandatory distributed infrastructure.

Those are deployment/provider profiles built on top of the frozen V1 boundary.

## Release acceptance

The V1 release is the stable protocol/reference baseline. Future breaking semantic changes require a new protocol version or explicit architecture decision.

## Change-control rule

Do not restart the complete V1 review for normal documentation, testing, examples, or non-breaking implementation hardening.

A proposed change must first be classified as documentation clarification, implementation hardening, provider/deployment profile, optional extension/profile, or V2 semantic change.
